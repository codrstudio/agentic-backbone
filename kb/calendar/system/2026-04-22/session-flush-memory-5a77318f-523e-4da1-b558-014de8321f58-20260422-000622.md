**Intervalo de checagem: 3–10s, nunca mais.** Conversas entre agentes exigem dinamismo. Se você só checa a cada 60s+, o humano vai reclamar — e ele tem razão. O `chat-watcher.sh` polla a cada 3s por default, e você pareia ele com a ferramenta `Monitor` pra receber notificação em tempo real a cada novo evento.

**NUNCA use `ScheduleWakeup` pra monitorar agent-chat.** O mínimo dele é 60s e as heurísticas de cache TTL (270s/1200s) fazem sentido pra tarefas idle — agent-chat é interativo, regra oposta. Use Monitor ou nada.

### O bug do `tail -n 1` — NÃO USE

`tail -n 1 .tmp/-chat.txt` **retorna string vazia** quando o arquivo termina com `\n\n` (que é o caso normal após `cat >> ... << EOF` com linha em branco antes do `EOF`). A "última linha" é o nada depois do último `\n`.

Consequência: o loop nunca detecta `"$ME>"` porque está comparando com `""`. O agente fica preso achando que é vez do outro quando na verdade é sua vez.

**Use `awk 'NF{last=} END{print last}'`** — pega a última linha **não-vazia**, robusto contra trailing newlines.

### O bug do stdout perdido em `run_in_background`

`Bash(run_in_background: true)` com loop longo + `sleep` tem condição em que o task runner mata o processo durante o sleep e perde qualquer `echo` acumulado. Notificação chega com `status=completed` mas output file tem **0 bytes**. Histórico observado: ~70% dos monitors com loop longo falham desse jeito.

**Solução: escrever eventos em arquivo do workspace, não em stdout.** `echo "..." >> .tmp/-chat-events.log` sobrevive a qualquer kill — é flush-a-cada-linha no filesystem local.

### Watcher daemon (canônico)

A skill inclui `chat-watcher.sh` em `${skill_dir}/chat-watcher.sh`. Aceita 3 args:

```bash
bash chat-watcher.sh <me_id> [chat_path] [events_path]
```

- `me_id` — seu identificador (ex: `nic`, `hub`, `portal`)
- `chat_path` — default `.tmp/-chat.txt` (caminho canônico); passe explícito se o chat vive em outro lugar (ex: `/d/.tmp/chat.txt`)
- `events_path` — default `.tmp/-chat-events.log` (idem)

O watcher polla mtime do chat a cada 3s. Tipos de evento:

- `START me=X pid=N chat=...` — watcher iniciou (só events file)
- `INIT last='...' mtime=N` — estado no primeiro check (só events file)
- `CHANGE last='...' mtime=N` — arquivo mudou (só events file)
- `SIGNAL=${me_id}>` ou `SIGNAL=END>` — **stdout + events file**; watcher sai com `exit 0`
- `ERROR chat_not_found=...` — **stdout + events file**

Eventos de **ação** (`SIGNAL=`, `ERROR`) vão em stdout **e** no events file. Eventos de estado só no events file. Separação intencional: o stdout é o canal de notificação; mandar CHANGE pra ele polui o chat sem motivo.

### Pareamento com a ferramenta Monitor (primária)

Monitor transforma cada linha de stdout do watcher em notificação que acorda Claude — sem `ScheduleWakeup`, sem humano re-invocando. Esse é o padrão:

```
Monitor({
  command: 'bash "C:/.../agent-chat/chat-watcher.sh" nic /d/.tmp/chat.txt /d/.tmp/chat-events.log',
  description: 'agent-chat: aguardando turno (me=nic)',
  persistent: true,
  timeout_ms: 3600000
})
```

- `persistent: true` — watcher vive pela sessão; `TaskStop` pra cancelar
- Notificação chega quando watcher emite `SIGNAL=${me_id}>` (é sua vez) ou `SIGNAL=END>` (conversa fechou) ou `ERROR`
- Nesse momento, você lê o chat, responde, posta a deixa do outro, e inicia **novo** Monitor (o anterior já saiu com exit 0)

### Alternativa sem Monitor (fallback)

Rodar o watcher em `Bash(run_in_background)` e ler o events file manualmente:

```bash
nohup bash "$SKILL_DIR/chat-watcher.sh" nic > /dev/null 2>&1 &
```

Nesse modo você tem que re-entrar Claude periodicamente pra ler o log — só serve se Monitor não estiver disponível. Mesmo aqui, re-entrada deve ser ≤10s (impraticável via ScheduleWakeup, daí a preferência pelo Monitor).

### Como saber se é sua vez

**Primário**: Monitor (acima) notifica automaticamente quando o watcher emite `SIGNAL=${ME}>` ou `SIGNAL=END>`.

**Sanity check** antes de agir como "é minha vez": a notificação contém a linha do watcher (`... SIGNAL=nic>`). Confirme com:

```bash
awk 'NF{last=} END{print last}' .tmp/-chat.txt
```

Se retornar `${ME}>`, confirmado. Se não, o chat avançou depois do evento — releia o arquivo inteiro.

**Fallback** (sem Monitor): leia o events file manualmente:

```bash
tail -n 20 .tmp/-chat-events.log
```

Se você vê `SIGNAL=${ME}>` no final → é sua vez, responda.
Se você vê só `START`/`INIT` sem `SIGNAL` → watcher ainda rodando, verifica se processo existe (`ps`). Se não existir, o watcher morreu silenciosamente; reinicie.
Se você vê `CHANGE last='outro_id>'` recente sem `SIGNAL` → o outro postou mas não terminou com sua deixa; leia o chat pra entender.

**Verificação de integridade** antes de agir como "é minha vez":

```bash
awk 'NF{last=} END{print last}' .tmp/-chat.txt
```

Se retornar `"$ME>"`, confirmado. Se não, o log mentiu ou o chat avançou depois.

### Ciclo de vida do watcher

- **Um watcher por turno de espera.** Depois que ele sinaliza `SIGNAL=mestre>` e sai, você responde e inicia outro watcher.
- **Não deixa múltiplos watchers rodando simultaneamente** — eles competem pelo mesmo evento e poluem o log. Antes de iniciar um novo, confere `ps -ef | grep chat-watcher` e mata órfãos com `kill PID`.
- **Watcher morto silenciosamente**: se entre turnos você vê que o watcher não está no `ps` e o log não tem `SIGNAL`, reinicie-o imediatamente. Pode ter havido mudanças no chat durante o downtime — rode a verificação de integridade.

## Comunicação entre agentes

- **Mantenham-se informados.** Cada agente deve contar ao outro o que está fazendo. Antes de uma tarefa não-trivial, avise. Ao terminar uma entrega, avise. Formato livre — o importante é que o outro nunca fique no escuro.
- **Negocie APIs antes de implementar** componentes compartilhados. Poste interfaces TypeScript completas para o outro integrar.
- **Declare conflitos.** Se for tocar em arquivo que o outro pode estar editando, avise antes.
- **Seja direto.** Mensagens curtas e objetivas. Sem formalidades.
- **Um turno por vez.** Só escreva quando for sua vez (última linha = seu id, confirmado via `awk`).

## Fechamento

A conversa termina com **handshake de dois turnos** + sentinel `END>`:

1. Um agente propõe fechar, posta um resumo do seu lado, e devolve a deixa.
2. O outro confirma, resume seu lado, e escreve `END>` sozinho na última linha.

Quando `END>` aparece, ambos saem do loop de monitoramento e a skill encerra. Ninguém fica pendurado esperando.

Se alguém discordar do fechamento, devolve a deixa normal (`{outro_id}>`) em vez de `END>` e a conversa continua.
